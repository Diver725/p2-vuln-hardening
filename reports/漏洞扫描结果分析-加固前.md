## 三、详细分析

### P2-VULN-01：RETbleed 内核缓解缺失

**CVE**

- CVE-2022-29900
- CVE-2022-29901

**检测结果**

```text
/sys/devices/system/cpu/vulnerabilities/retbleed = Vulnerable
```

**验证结果**

- 三台 target 的 CPU 均为 Intel(R) Core(TM) i5-10300H。
- 内核启动参数中没有 `mitigations=off`。
- 当前 Linux 内核为 `6.8.0-139-generic`。
- 三台虚拟机结果完全一致。

**判断**

这是宿主机 CPU 微码、BIOS 和 VirtualBox 虚拟化环境共同影响的结果。客户机内部无法像修改 SSH 配置那样直接消除该问题。

**建议**

- 实验环境记录为残余风险。
- 生产环境应更新宿主机 BIOS、CPU 微码，并评估虚拟化平台 CPU 配置。
- 不在客户机上使用无效的 Ansible 包更新来“假装修复”。
- 如果确认宿主机已经完成微码更新，可在 GVM 中创建 Override 并记录原因。

### P2-VULN-02：Processor MMIO Stale Data 缓解缺失

**CVE**

- CVE-2022-21123
- CVE-2022-21125
- CVE-2022-21166

**检测结果**

```text
/sys/devices/system/cpu/vulnerabilities/mmio_stale_data =
Vulnerable: Clear CPU buffers attempted, no microcode; SMT Host state unknown
```

**判断**

系统明确报告 `no microcode`，说明宿主机 CPU 微码没有提供该缓解。该项属于宿主机基础设施问题。

**建议**

- 更新宿主机 BIOS 和 CPU 微码。
- 实验环境记录为残余风险。
- Ansible 只负责记录和复测，不强行修改客户机内核参数掩盖问题。

### P2-VULN-03：SSB 推测存储绕过缓解缺失

**CVE**

- CVE-2018-3639

**检测结果**

```text
/sys/devices/system/cpu/vulnerabilities/spec_store_bypass = Vulnerable
```

**判断**

与 CPU 和虚拟化配置相关，VM 内部没有独立的安全修复包可以解决。需要宿主机 BIOS/微码和虚拟化平台配合。

**建议**

- 记录为环境限制和残余风险。
- 不通过关闭 SELinux/内核安全功能等错误方式处理。
- 复测时确认状态是否因宿主机补丁而变化。

### P2-VULN-04：sqlite3 安全更新

**USN**

```text
USN-8775-1
```

**漏洞**

```text
CVE-2026-39113
CVSS 5.0 Medium
```

**检测结果**

```text
软件包：libsqlite3-0
当前版本：3.45.1-1ubuntu2.7
修复版本：>=3.45.1-1ubuntu2.8
```

**判断**

这是明确、真实且可修复的系统补丁问题。

**建议**

执行：

```bash
sudo apt update
sudo apt install --only-upgrade libsqlite3-0
```

后续通过 Ansible 的 apt 模块并在三台 target 上统一执行。

### P2-VULN-05：SSH 弱 MAC 算法

**检测结果**

SSH 同时支持以下弱 MAC：

```text
umac-64-etm@openssh.com
umac-64@openssh.com
```

**判断**

低风险信息泄露/算法强度问题，适合通过 SSH 配置禁用。

**建议**

在 `/etc/ssh/sshd_config.d/` 下增加独立的加固文件，明确设置允许的 MAC，排除 64 位弱算法。修改后先进行语法检查，再重启 SSH，并保留当前管理连接用于回滚。

### P2-VULN-06：TCP Timestamps 信息泄露

**检测结果**

主机启用 TCP Timestamp，可用于推断主机运行时间。

**建议**

在 sysctl 配置中将：

```text
net.ipv4.tcp_timestamps = 0
```

作为低风险加固项处理。该修改会影响 TCP RTT 估算精度，但在当前实验环境中可接受。

### P2-VULN-07：ICMP Timestamp 信息泄露

**检测结果**

主机响应 ICMP Timestamp Request。

**建议**

优先通过 UFW/nftables/iptables 阻止 ICMP timestamp 请求，而不是直接关闭所有 ICMP。该问题属于低风险信息泄露项。

## 四、Ansible 加固映射

| 问题 | Ansible 处理方式 |
|---|---|
| USN-8775-1 | `apt` 更新 `libsqlite3-0` |
| SSH 弱 MAC | 部署 `sshd_config.d` 配置片段并做 `sshd -t` 检查 |
| TCP Timestamps | 部署 sysctl 配置文件并执行 `sysctl --system` |
| ICMP Timestamp | UFW 规则拦截 |
| CPU 侧信道 | 仅记录残余风险和宿主机依赖，不在客户机强行修复 |
| 复测 | 重新执行 Lynis 和 GVM 完整扫描 |

## 五、加固后复测标准

加固后需要重新执行：

1. Lynis 基线扫描。
2. GVM 完整扫描。
3. 对比加固前后结果。

重点验证：

- `libsqlite3-0` 升级到修复版本。
- `USN-8775-1` 从扫描结果中消失。
- SSH 弱 MAC 算法结果消失。
- TCP Timestamps 结果消失。
- ICMP Timestamp 结果消失或由防火墙拦截。
- CPU 侧信道结果如仍存在，应记录为宿主机环境残余风险，而不是错误地标记为已修复。
