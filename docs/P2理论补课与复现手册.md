# P2 理论补课与复现手册

> 用途：补足 P2 中由助手代做较多、但需要自己理解的核心理论和流程。
>
> 学习节奏：先理解，再跟做，最后独立复现。不要在还没有理解时直接背命令。

## 一、学习方式

每个模块都按五步进行：

```text
1. 理解原理
2. 观察现有环境
3. 跟着助手完整做一次
4. 用自己的话复述
5. 独立复现
```

任务卡用于第五步，不作为第一步直接考核。

## 二、P2 理论学习地图

| 模块 | 主题 | 目标 |
|---|---|---|
| M1 | SSH 隧道与安全访问 | 理解为什么要建立隧道，以及数据如何到 GVM |
| M2 | GVM 架构与 Feed | 理解 gvmd、OpenVAS、PostgreSQL、Web UI 和漏洞库的关系 |
| M3 | 漏洞扫描流程 | 理解 Credential、Target、Port List、Scan Config 和 Task |
| M4 | 扫描结果分析 | 理解 Severity、CVSS、QoD、CVE、误报和残余风险 |
| M5 | Ansible 基础 | 理解 inventory、module、task、playbook、handler 和幂等性 |
| M6 | Linux 加固 | 理解 SSH、UFW、sysctl、补丁、审计和登录防护 |
| M7 | 漏洞闭环 | 理解扫描、验证、整改、复测、报告和风险接受 |

学习顺序固定为：

```text
M1
→ M2
→ M3
→ M4
→ M5
→ M6
→ M7
```

# M1：SSH 隧道与安全访问

## 1. 要解决的问题

GVM 的 Web 服务运行在：

```text
p2-mgmt 虚拟机内部
127.0.0.1:443
```

这里的 `127.0.0.1` 表示“只接受 p2-mgmt 自己访问”。

主机浏览器不能直接访问：

```text
http://192.168.10.10:443
```

原因：

- GVM 的 Web 端口没有绑定到 `0.0.0.0`。
- 它只监听 `p2-mgmt` 的回环地址 `127.0.0.1`。
- 外部主机无法直接访问另一台机器的回环地址。

## 2. 为什么不直接把 GVM 端口暴露出来

如果改成：

```text
0.0.0.0:443
```

虽然浏览器能直接访问，但会产生问题：

- 网络内其他主机也可能访问 GVM 控制台。
- GVM 是高权限安全管理界面。
- 考试实验和真实环境中，管理控制台应减少暴露面。
- 直接开放端口容易增加被扫描、暴力破解和误操作的风险。

所以使用 SSH 隧道：

```text
只在主机本机开放一个临时端口
→ 通过已经加密的 SSH 连接访问 GVM
```

## 3. 隧道命令拆解

使用命令：

```powershell
ssh -N -L 9444:127.0.0.1:443 lab@192.168.10.10
```

逐段解释：

| 部分 | 作用 |
|---|---|
| `ssh` | 使用 SSH 客户端建立加密连接 |
| `-N` | 不执行远程命令，只建立端口转发 |
| `-L` | 建立本地端口转发 |
| `9444` | 主机本地监听的端口 |
| `127.0.0.1` | 从 `p2-mgmt` 的角度看的目标地址 |
| `443` | GVM nginx 的 HTTPS 端口 |
| `lab` | 登录 p2-mgmt 的 Linux 用户 |
| `192.168.10.10` | p2-mgmt 的 host-only IP |

关键理解：

```text
-L 本地端口:远端目标地址:远端目标端口 用户@SSH服务器
```

其中：

```text
远端目标地址和端口
=
从 SSH 服务器 p2-mgmt 的角度去连接
```

## 4. 数据路径

浏览器访问：

```text
https://127.0.0.1:9444
```

实际流量路径是：

```text
主机浏览器
→ 主机 127.0.0.1:9444
→ SSH 加密隧道
→ p2-mgmt
→ p2-mgmt 的 127.0.0.1:443
→ nginx
→ GVM Web 界面
```

返回数据再沿原路返回浏览器。

## 5. 为什么是 443 而不是 9392

这版 Greenbone Compose 中：

```text
nginx 的 HTTPS Web 入口绑定在 127.0.0.1:443
```

最初使用：

```text
9444 → 127.0.0.1:9392
```

浏览器出现：

```text
ERR_SSL_PROTOCOL_ERROR
```

说明浏览器把 HTTPS 请求发到了一个不等于预期的服务端口。

改为：

```text
9444 → 127.0.0.1:443
```

后成功打开 GVM 登录页面。

## 6. SSH 隧道和代理 TUN 的区别

SSH 隧道：

```text
访问 GVM Web 管理页面
通过 SSH 加密连接
走 host-only 网络
不需要代理 TUN
```

代理 TUN：

```text
用于访问互联网、下载镜像
会影响虚拟机的 DNS 和 NAT 流量
与 GVM Web 登录不是同一件事
```

两者不要混为一谈。

## 7. 隧道为什么重启后会断开

SSH 隧道是一个正在运行的 `ssh` 进程。

当出现以下情况时，隧道会结束：

- 关闭 PowerShell 窗口
- p2-mgmt 重启
- SSH 连接断开
- 主机睡眠或网络变化

隧道结束后：

```text
主机 127.0.0.1:9444 不再监听
```

因此浏览器会报连接拒绝或 SSL 错误。

重新执行隧道命令即可。

## 8. 验证方法

### 检查本地端口

在主机 PowerShell：

```powershell
Test-NetConnection 127.0.0.1 -Port 9444
```

正常：

```text
TcpTestSucceeded : True
```

### 检查隧道 SSH 进程

```powershell
Get-Process ssh
```

应能看到 `ssh` 进程。

### 检查 GVM 远端端口

在 p2-mgmt 内：

```bash
curl -kI https://127.0.0.1:443
```

正常返回 `200` 或 `302`。

## 9. 常见错误

| 错误 | 常见原因 |
|---|---|
| `Permission denied` | SSH 密码错误 |
| `Address already in use` | 本地 9444 已占用，换端口 |
| `ERR_CONNECTION_REFUSED` | 隧道没建立或已断开 |
| `ERR_SSL_PROTOCOL_ERROR` | 转发到了非 HTTPS 端口 |
| 隧道窗口立即回到提示符 | SSH 登录失败或端口转发失败 |

## 10. 学完后的复述要求

请用自己的话回答：

1. 为什么不能直接从主机浏览器访问 `192.168.10.10:443`？
2. `-L 9444:127.0.0.1:443` 中第一个 `127.0.0.1` 是谁的角度？
3. 为什么关闭 PowerShell 后 GVM 页面打不开？
4. SSH 隧道和代理 TUN 的区别是什么？
5. 为什么浏览器最终访问的是 `https://127.0.0.1:9444`？

## 11. 独立复现标准

在不看本手册命令的情况下：

1. 重新建立 SSH 隧道。
2. 使用不同本地端口，例如 `9555`。
3. 验证本地端口监听。
4. 打开 GVM 页面。
5. 解释整条数据路径。

# M2：GVM 架构与 Feed

## 组件分工

| 组件 | 作用 |
|---|---|
| nginx / GSA | Web 页面和 HTTPS 入口 |
| gsad | Web/API 与 GVM 管理协议之间的接口 |
| gvmd | 管理核心，负责任务、用户、目标和调度 |
| pg-gvm | PostgreSQL，保存用户、任务、配置和结果 |
| redis-server | 扫描过程临时数据 |
| ospd-openvas / openvasd | 扫描侧组件，连接目标并执行检测 |
| Feed | 提供检测规则与漏洞知识 |

数据流：

```text
浏览器
→ nginx
→ gsad
→ gvmd
→ ospd-openvas / openvasd
→ target
→ gvmd
→ PostgreSQL
→ Report
```

`gvmd` 是管理调度器，不负责自己直接探测目标。

## Feed 类型

```text
NVT = 检查脚本和检测逻辑
SCAP = CVE、CPE 和漏洞关联数据
CERT = 厂商安全公告
Notus = 软件包版本漏洞数据
GVM_DATA = 扫描配置、端口列表、报告格式
```

Feed 不完整时，扫描结果会不准确或覆盖不足，可能表现为漏报、缺少 CVE 关联或报告信息不完整。

## 凭据与证据

```text
无凭据扫描 → 主要看网络服务和外部暴露面
有凭据扫描 → 可以读取软件包、内核状态和系统配置
```

例子：

| 问题 | 是否需要 SSH 凭据 |
|---|---|
| SSH 弱 MAC | 通常不需要 |
| sqlite 软件包版本 | 通常需要 |
| RETbleed sysfs 状态 | 需要 |

# M3：漏洞扫描配置

## 核心关系

```text
Credential  → 用什么身份登录
Target      → 扫描谁
Port List   → 扫描哪些端口
Scan Config → 执行哪些漏洞测试
Scanner     → 谁来执行
Task        → 组合配置并启动
Report      → 一次运行的结果快照
```

## Task 和 Report

```text
Task 可以重复运行
每次运行生成新的 Report
Task 保存配置
Report 保存某一次执行的结果
```

常见状态：

```text
New → Requested → Queued → Running → Done
Stopped / Interrupted
```

只有覆盖完整目标的 `Done` 报告，才适合作为最终基线。

## 高级参数

| 参数 | 作用 |
|---|---|
| Alive Test | 判断目标是否在线 |
| Add results to Assets | 将结果写回资产库 |
| Apply Overrides | 应用预定义的风险例外规则 |
| Min QoD | 过滤低可信度结果 |
| NVTs per host | 单台主机并发执行的检测数 |
| Concurrently scanned hosts | 同时扫描的主机数 |
| Schedule | 手动或定时扫描 |
| Auto Delete Reports | 报告保留策略 |

并发越高越快，但 CPU、内存、网络和目标负载也越高。

# M4：扫描结果分析

## 核心字段

```text
Severity = CVSS 分级后的结果
CVSS = 漏洞理论严重性评分
QoD = 检测可信度
CVE = 公开漏洞编号
Host = 哪台主机
Port = 哪个端口
Location = 从哪个位置或服务检测到
```

注意：

```text
CVSS 高 ≠ QoD 高
CVSS 高 ≠ 一定由客户机修复
CVSS 高 ≠ 当前环境一定可利用
```

## 结果状态

```text
True Positive = 真实存在
False Positive = 验证后不存在或不适用
Fixed = 已修复且复测消失
Mitigated = 未根除，但被其他控制措施降低风险
Accepted Risk = 确认存在，但当前接受并记录
```

## 修复优先级

不能只按 CVSS 排序，还要考虑：

```text
严重性
+ 检测可信度
+ 暴露面
+ 可利用性
+ 修复成本
+ 业务影响
+ 补偿措施
```

风险可粗略理解为：

```text
风险 = 影响 × 可能性
```

## 实际案例

| 问题 | 分类 | 处理 |
|---|---|---|
| libsqlite3-0 旧版本 | True Positive | Ansible 更新，复测确认 Fixed |
| SSH 弱 MAC | True Positive | 收紧 SSH 配置，Fixed |
| TCP timestamps | True Positive | sysctl 关闭，Fixed |
| ICMP timestamp | True Positive | UFW 默认拒绝入站，Mitigated/Fixed |
| CPU 侧信道 | True Positive | 宿主机微码/虚拟化限制，Accepted Risk |

# M5：Ansible 基础

## 角色与连接模型

```text
控制机：p2-mgmt
被管理机：p2-target-1/2/3
连接方式：SSH + 目标机 Python + Ansible Module
```

可以把模型记成：

```text
Inventory = 地址簿
SSH = 安全运输通道
Python = 目标机执行环境
Module = 标准操作工具
Result = JSON 回执
```

Ansible 的 `ping` 模块不是 ICMP Ping。它验证：

```text
SSH 可连接
Python 可使用
模块可执行
结果可返回
```

## Inventory

Inventory 定义：

```text
管理哪些主机
主机对应的 IP
使用哪个 SSH 用户
主机属于哪个组
```

示例组：

```ini
[targets]
p2-target-1 ansible_host=192.168.10.11
```

## Playbook 结构

```text
Play
├── name
├── hosts
├── become
├── gather_facts
└── tasks
    ├── Task
    │   ├── name
    │   ├── module
    │   └── module arguments
    └── Handler
```

概念：

```text
Play = 对一组主机执行的一套配置
Task = 一个具体操作
Module = 执行操作的工具
Handler = 被 notify 触发的任务
Variable = 可复用的配置值
```

## 幂等性

```text
第一次执行：根据当前状态做必要修改
第二次执行：状态已满足，不再重复修改
```

常见状态：

```text
ok        = 已经是期望状态
changed   = Ansible 进行了修改
failed    = 执行失败
skipped   = 条件不满足，跳过
unreachable = 无法连接
```

优先使用幂等模块：

```text
apt
copy
lineinfile
service
sysctl
```

`command` 和 `shell` 不是天然幂等，需要额外控制。

## 执行参数

| 参数 | 作用 |
|---|---|
| `--syntax-check` | 检查 YAML 和 Playbook 结构，不执行 |
| `--limit` | 限制只对某台或某组主机执行 |
| `-K` | 提示输入 sudo/become 密码 |
| `--diff` | 显示配置修改前后差异 |
| `--check` | 模拟执行 |
| `-i` | 指定 Inventory |
| `-v` / `-vvv` | 增加执行信息 |

安全执行顺序：

```text
语法检查
→ 单台 target 执行
→ 验证 SSH、服务和管理链路
→ 批量执行其余目标
→ Lynis/GVM 复测
```

# M6：Linux 安全加固

## 加固目标

```text
减少攻击面
降低漏洞可利用性
增加检测和审计能力
保持系统可管理
```

## 已实施或重点讲解的加固方向

### 补丁与软件包

```text
apt update = 更新软件源索引
apt upgrade = 更新已安装软件包
apt full-upgrade = 处理依赖关系变化
```

修复后必须检查版本，并通过 Lynis/GVM 复测。

### SSH

重点参数：

```text
PermitRootLogin no
MaxAuthTries 3
MaxSessions 2
X11Forwarding no
AllowAgentForwarding no
AllowTcpForwarding no
ClientAliveInterval 300
ClientAliveCountMax 2
TCPKeepAlive no
LogLevel VERBOSE
MACs...
```

设计取舍：

```text
暂时保留 PasswordAuthentication yes
→ 让 GVM 继续使用用户名+密码扫描
```

生产环境应逐步改为专用扫描账号和 SSH 密钥。

### UFW

```text
Default incoming deny
Default outgoing allow
22/tcp 只允许 192.168.10.0/24
```

必须先放行 SSH，再启用 UFW，避免管理失联。

### sysctl

重点参数：

```text
net.ipv4.tcp_timestamps = 0
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.default.accept_redirects = 0
net.ipv4.conf.all.accept_source_route = 0
net.ipv4.conf.default.accept_source_route = 0
net.ipv4.conf.all.rp_filter = 1
net.ipv4.conf.default.rp_filter = 1
net.ipv4.conf.all.log_martians = 1
net.ipv4.icmp_echo_ignore_broadcasts = 1
net.ipv4.icmp_ignore_bogus_error_responses = 1
fs.suid_dumpable = 0
```

配置文件持久化，`sysctl --system` 立即加载。

### 密码策略与 fail2ban

```text
pam_pwquality：密码长度和字符复杂度
login.defs：密码有效期、警告期、umask
MAXAuthTries：限制单次 SSH 连接尝试次数
fail2ban：统计来源 IP 的重复认证失败并动态封禁
```

区别：

```text
MaxAuthTries = 单次连接限制
fail2ban = 跨连接、按来源 IP 统计并封禁
```

### 审计与性能

```text
auditd  = 记录安全相关行为和系统调用
sysstat = 记录 CPU、内存、磁盘、网络等性能历史
```

### 敏感信息保护

```text
限制 core dump
限制 setuid 程序 core dump
登录警告横幅
```

### 文件权限、SUID 与服务最小化

```text
/etc/shadow 权限应严于 /etc/passwd
异常 SUID 程序先评估用途，不直接删除
不必要服务不安装、不启动、不开机自启、不对网络开放
```

发现异常 SUID：

```bash
find / -xdev -perm -4000 -type f 2>/dev/null
```

检查监听端口：

```bash
sudo ss -lntup
```

检查开机服务：

```bash
systemctl list-unit-files --type=service --state=enabled
```

## 加固后的验证要求

```text
SSH/Ansible 仍可管理
GVM 凭据仍可登录
服务监听仍符合预期
Lynis 评分改善
GVM 可修复漏洞消失
残余风险有明确记录
```

# M7：漏洞闭环与报告

## 漏洞管理不等于漏洞扫描

完整流程：

```text
资产清点
→ 扫描范围和策略
→ 执行扫描
→ 验证与分诊
→ 优先级排序
→ 整改
→ 复测
→ 结果分类
→ 报告与持续管理
```

扫描只负责发现问题，管理负责把问题处理到可解释、可验证、可追踪的状态。

## 结果状态

```text
Fixed = 已修复并复测确认
Mitigated = 未根除，但通过其他控制降低风险
False Positive = 验证后不存在或不适用
Accepted Risk = 确认存在但当前接受，需记录理由和后续计划
Open = 仍未处理
```

## GVM Override

Override 是结果例外规则，不是漏洞修复。

使用 Override 必须记录：

```text
原因
证据
审批
有效期
复测条件
```

不能把 Override 当成让报告变好看的手段。

## 漏洞报告结构

推荐包含：

```text
概述
扫描环境
扫描方法
结果总览
重点发现
详细分析
整改与复测
残余风险
结论
附录
```

重点发现至少说明：

```text
问题名称
严重等级
影响主机
CVE/CVSS/QoD
证据
风险判断
修复动作
当前状态
复测结果
```

## 报告原则

```text
结论先行
证据可追溯
风险有等级
整改有动作
复测有结果
残余风险有责任和计划
```

## 常用管理指标

```text
严重等级分布
修复率
平均修复时间 MTTR
资产覆盖率
误报率
残余风险数量
逾期漏洞数量
```

## 变更与闭环原则

```text
先快照
→ 单台测试
→ 验证管理链路
→ 批量执行
→ 保留回滚方案
→ 复测
→ 报告闭环
```

先单台测试的目的是降低变更爆炸半径，避免一次错误配置同时影响全部目标。
